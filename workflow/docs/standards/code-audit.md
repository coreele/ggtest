# 代码审计标准

## 目的与适用范围

本规范规定对仓库 **`src/`** 源码做静态代码质量审计时的检查条款，以及审计中须单独列出的关注项（Known Issue、Tech Debt、优化机会）。

**适用：** 代码审计 / code-audit skill 对照本文件及同前缀扩展文件审查实现代码。

**不适用：** Feature 工作流中的验证门禁、DoD、Review/QA 流程——那些见 [quality.md](./quality.md)，代码审计**不**依据该文件。

## 1. 结构与职责

- 模块/类应有单一清晰职责；禁止无关关注点堆在同一类型中。
- 包与目录边界应反映依赖方向；禁止下层依赖上层、循环依赖。
- 公开 API 面应最小；内部实现不得无必要暴露为 public。

## 2. 正确性与边界

- 公共方法须处理可预见的非法输入、空值与边界条件，或在合同中明确前置条件并由调用方保证。
- 错误路径须可观察：抛出有意义的异常或返回明确失败结果；禁止吞掉异常后继续错误状态。
- 共享可变状态须有明确并发约定；无约定时不得假定单线程安全。

## 3. 可读性与命名

- 类型、方法、变量名须表达意图；禁止误导性命名与无意义缩写（惯用短名如 `i`、`sb` 除外）。
- 控制流深度应可控；过深嵌套须拆分方法或提前返回。
- 注释只解释「为什么」或非显而易见的约束；禁止复述代码字面含义的注释，禁止保留失效注释。

## 4. 重复与复杂度

- 禁止明显可抽取的重复逻辑在多处漂移修改。
- 单个方法过长或分支过多时，须拆分为可命名的小单元，除非领域算法本身要求内聚在一处并有注释说明。

## 5. 资源与副作用

- I/O、连接、流等资源须在所有退出路径正确关闭或移交所有权（如 try-with-resources）。
- 副作用（写库、写文件、出站网络）应集中在明确边界；解析/纯计算层不得隐式发起 I/O。

## 6. 依赖与测试友好

- 核心逻辑应可在不启动完整外部系统的情况下被单测覆盖；对 DB/网络等边界使用接口或可替换实现。
- 测试代码（`src/test`）不得降低生产代码的封装来迁就测试，除非有明确的测试夹具约定。
- 禁止仅恒真、不断言行为的测试冒充覆盖（若审计范围包含测试源码）。

## 7. 敏感信息与配置

- 禁止在源码中硬编码密钥、令牌、生产凭据或含凭据的连接串。
- 配置与密钥须来自环境、配置文件（未提交的本地机密）或注入；审计发现疑似机密时报告位置，不得在报告中回显完整秘密值。

## 8. 关注项：Known Issue / Tech Debt / 优化

审计除违规 Findings 外，须单独收集下列**关注或优化**项（可记为 Info/Low，或专用「关注项」表；不得与 Critical 违规混为一谈）：

| 类型 | 含义 | 须记录 |
|---|---|---|
| Known Issue | 已知缺陷或错误行为；代码/注释/`FIXME`/`BUG`/`XXX` 已暗示，或逻辑上可复现但暂未修 | 位置、现象、影响面、是否有临时规避 |
| Tech Debt | 可工作但拖累演进的实现：过时 API、临时方案残留、错误抽象、缺失边界、测试缺口 | 位置、债务描述、若不还清会怎样、建议偿还方向 |
| 优化机会 | 非必须立刻改、但值得改进：性能热点迹象、API 清晰度、结构简化、重复可收敛 | 位置、现状成本、预期收益、建议优先级 |

**必须：**

- 扫描范围内的 `TODO` / `FIXME` / `HACK` / `XXX` / `TECHDEBT` 等标记，归入上表相应类型。
- 若存在登记册 [`code-audit-register.md`](./code-audit-register.md)，核对其中条目：仍存在则更新状态；已消失则在报告中标记 resolved 建议。
- 每条关注项给出可执行的下一步（修 bug / 开工作项 / 观测 / 明确接受并登记）。

**禁止：**

- 把纯风格偏好写成 Known Issue。
- 把未证实的猜测写成 Known Issue；证据不足时标为「待确认」并说明缺什么证据。

## 9. 审计结论用法

- Finding（违规）须可定位到文件与行（或符号），并引用本标准章节编号。
- 关注项引用 §8，并标注类型（Known Issue / Tech Debt / 优化）。
- 级别建议：Critical（正确性/安全硬伤）、High（高概率缺陷或严重可维护性）、Medium（明确违规但影响局部）、Low/Info（风格、关注项、改进建议）。
- 本标准未覆盖的风格偏好不得升格为 Critical/High。

## 10. 可扩展性

本标准可按文件扩展，**无需修改** code-audit skill：

| 扩展方式 | 约定 | 说明 |
|---|---|---|
| 专项标准 | `workflow/workflow/docs/standards/code-audit-<topic>.md` | 语言、模块、性能、并发等专项条款；与本文件一并加载（通配排除登记册） |
| 关注项登记册 | `workflow/workflow/docs/standards/code-audit-register.md` | 持久化 Known Issue / Tech Debt / 已接受风险；存在则必读核对，**不**当作条款标准 |
| 用户点名 | 任意其他 `workflow/workflow/docs/standards/*.md` | 仅当用户明确指定时追加；默认仍不加载 `quality.md` 等流程规范 |

**专项标准文件结构（建议）：**

1. 目的与适用范围（写明相对本文件是补充还是收窄）
2. 必须 / 禁止 / 允许条款（可检查、可定位）
3. 可选：本专项下的关注项示例或登记指针

**冲突处理：** 专项与本文件冲突时，专项仅在其声明的适用范围内优先；报告须注明采用了哪条。无法判断时以更严格条款为准并说明。

**版本演进：** 新增/修改条款后，下次审计即生效；对存量代码的新条款违规，优先记 Tech Debt 或分阶段整改建议，除非属于 Critical 正确性/安全问题。
