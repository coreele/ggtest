# 文档工程规范

Docs as Code：与相关代码同仓库、同分支、同审阅演进。

| 部分 | 内容 |
|---|---|
| A. 文档工程 | 分类主责、Plan 文档影响、用户/运维最低要素、链接校验、审阅职责 |
| B. 工作流产物整理 | 交接前可读优先的原位自检（不依赖独立 skill） |

**主责概览：** Developer 维护开发文档；Reviewer 检查文档影响；QA 验收用户可见或运维可执行文档。

---

## A. 文档工程

### A.1 分类与主责

| 类型 | 主责 | 典型路径 |
|---|---|---|
| 开发 / API / 配置 | Developer | 代码注释、README、接口与配置说明 |
| 架构决策 | Planner | `features/<id>/design.md`、ADR |
| 界面与交互（按需） | Planner | `features/<id>/ui-design.md` |
| 部署与排障 | DevOps | `workflow/docs/deploy/` |
| Spec | Analyst | `features/<id>/spec.md` |
| 工作项与流程 | Manager | `workflow/docs/manager/`、工作项记录 |

只改本职文档；跨角色变更须在 Plan「文档影响」中声明。工作流产物结构见模板与 `workflow/docs/README.md`；交接前整理见 **B**。

### A.2 Plan 文档影响

每个 Plan 须分别说明三类文档的更新路径；无需更新则标 `N/A` 并写理由：

- **开发文档** — 注释、API、配置、开发者 README 等
- **用户文档** — 功能说明、操作指南等
- **运维文档** — 部署、监控、排障、备份恢复等

### A.3 用户 / 运维文档最低要素

适用于**用户可见**与**运维可执行**文档：

| 要素 | 要求 |
|---|---|
| 适用对象 | 必须 |
| 前置条件 | 必须 |
| 操作步骤 | 必须 |
| 预期结果 | 必须 |
| 失败处理 | 适用时 |

工作流产物（`spec` / `design` / `ui-design` / `plan` / `dev-notes` / `review` / `qa-report`、工作项记录、STATUS）与纯架构笔记**不**套本表；按各自模板 + **B** 整理。开发 / API / 配置文档若面向执行步骤则适用本表，否则以清晰可验证为准。

### A.4 链接与示例校验

Review 或 QA 须核验：内外链接、路径、命令与脚本示例、配置与代码片段。可用：实跑、对照仓库结构、确认可访问。错误引用须在合并前修正。

### A.5 Reviewer 与 QA

**Reviewer：** Plan「文档影响」是否完整；实现是否与声明一致。

**QA：** 验收用户可见与运维可执行文档（对照 Spec / Plan 与 A.3）。未通过则退回主责角色修正后复验。

## B. 工作流产物写作与轻度整理

**对象：** `spec.md`、`design.md`、`ui-design.md`、`plan.md`、`dev-notes.md`、`review.md`、`qa-report.md`、工作项记录（含归档 `manager.md`）。

**时机：** 初稿或阶段更新完成后、交接前；每次只处理一份文件。路径：`features/<feature-id>/` 根目录。

目标是**更好扫读**，不是更短。本节不替代 A 的主责与验收规则。

### B.1 原则

| 原则 | 含义 |
|---|---|
| 可读优先 | 顺着标题与模板扫读；不为缩短牺牲衔接句或必要背景 |
| 轻度整理 | 只删无信息量的复述与套话；禁止电报体、关键词堆砌、表内+表下双份 |
| 结构服从模板 | 枚举 / 链接 / 短标签在表内；长理由与背景进段落或「进度笔记」 |
| 语义保全 | 不改合同、结论、门禁强度与可验证性；存疑则保留 |

### B.2 步骤

1. 读初稿、模板与直接依据。
2. **必须保留：** 规范强度词（必须 / 禁止 / 允许）及条件例外；ID / 路径 / 命令 / 状态 / 枚举；合同、验收、证据、结论、风险、阻塞与恢复条件；模板必填项；不重复的简短背景。
3. **允许：** 合并相邻同义复述（保留更易扫读的一处）；验收 / Review 保持「要求 → 证据 → 结果」；阻塞保持「未验证项 → 原因 → 风险 → 恢复条件 → 复测范围」；删纯套话；并列事实可用列表（勿为列表化拆碎清晰短段）。
4. **禁止：** 单元格内长句理由（如 `skipped（长说明）`）；表下用电报体重抄整表；多字段挤一行；为缩短折断链接 / 路径；删掉仍有区分度的背景「只为变短」；压成含糊结论或缺主语。
5. 对照初稿核对保留项与模板结构。不确定则保留原文。

只改本职文档；不臆造字段。模板缺项报告作者补充，不得猜值。

### B.3 示例

**同义复述 → 合并**

整理前：

> P0-2 要求超过 10 MiB 的文件返回 `IMPORT_FILE_TOO_LARGE`，且不得创建数据库记录。10 MiB + 1 byte 文件返回该错误码，新增记录为 0，因此 P0-2 已通过。这里再次说明，错误码正确并且数据库没有产生记录。

整理后：

> P0-2：超过 10 MiB 的文件必须返回 `IMPORT_FILE_TOO_LARGE`，且不得创建数据库记录。实测 10 MiB + 1 byte 返回该错误码，且未新增数据库记录。结果：通过。

**工作项记录：枚举进表，理由进笔记**

差：单元格与表下都写 `skipped（既有系统介绍……无新增行为合同）`。

好：单元格 `skipped`；进度笔记写「Spec 门禁跳过：既有系统介绍与架构文档化，无新增行为合同。」
